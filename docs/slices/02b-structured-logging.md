# Slice 2b: Structured logging

Not globally CRITICAL REVIEW. **CRITICAL REVIEW applies only to the inbound requestId header sanitization** (Section 2 below) — that's the one piece of this slice with an actual untrusted-input attack surface; everything else is internal formatting/plumbing. PRD refs: Section 14 (Observability — "Structured JSON logs with giveawayId in the MDC, plus a requestId per request"). BUILD_ORDER item 2b, inserted after slice 2a.

## 1. Structured JSON console output: Spring Boot's built-in support, no new dependency

**Verified against Spring Boot's own reference docs for this version line** (fetched directly, not recalled from memory): `logging.structured.format.console` is the property; three built-in formats ship with plain `spring-boot-starter-logging` (Logback) — **no extra dependency, no `logstash-logback-encoder`, nothing to add to `pom.xml`**:
- `ecs` (Elastic Common Schema)
- `gelf` (Graylog Extended Log Format)
- `logstash` (classic Logstash JSON format)

All three automatically include every MDC key-value pair in the emitted JSON object — this is the mechanism that gets `requestId` (and, later, `giveawayId`) into every log line for free, with no manual field-mapping code.

**Format chosen: `ecs`.** Set via `logging.structured.format.console=ecs` in `application.properties`. Reasoning: this project has no committed log aggregator yet (Render's own log stream is the only consumer right now, per slice 2a Section 7) — `ecs` (Elastic Common Schema) is a vendor-neutral, widely-adopted schema designed specifically to not lock a project into one platform, which fits "no committed destination yet" better than `gelf` (Graylog-specific) or even `logstash` (ELK-specific, though also broadly supported). If a specific log platform gets adopted later and prefers a different shape, this is a one-line property change, not a re-architecture — nothing else in this slice depends on which of the three formats is chosen, since the MDC-inclusion behavior is identical across all three.

Example of what one line will actually look like (per Spring Boot's own documented example shape, adapted to this app):
```json
{"@timestamp":"2026-01-01T10:15:00.067462556Z","log.level":"INFO","message":"startup guard passed: environment=DEV bachsMode=SANDBOX","process.thread.name":"main","service.name":"giveaway-trust-engine","log.logger":"com.giveaway.giveawaytrustengine.config.StartupGuardBeanFactoryPostProcessor","ecs.version":"8.11","requestId":"..."}
```
(`requestId` would only appear on a request-scoped log line — the startup guard's own lines run before any HTTP request exists, so they won't carry one; see Section 3.)

## 2. requestId per HTTP request — CRITICAL REVIEW on the sanitization path

**Decision: accept Render's `Rndr-Id` header, sanitized — not a generic client-supplied header name, and not inbound-ignored entirely.** Verified directly against Render's own docs page (fetched the actual page, not a search-engine summary, per the standing practice established after an earlier slice's citation mistake): "Render includes this same value in the `Rndr-Id` HTTP header — both in the request to your web service *and* in the response to the requesting client" ([render.com/docs/logging](https://render.com/docs/logging)). Render already assigns a request ID at the platform level and forwards it to this app via that header, specifically so application logs can be correlated with entries in Render's own log explorer using the same ID. Ignoring it and always generating a fresh, unrelated UUID would throw that correlation away for no benefit. So: **accepted, under the header name `Rndr-Id`, sanitized exactly as described below regardless of the fact that Render itself is usually the one setting it** — this app doesn't get to assume a header is trustworthy just because of which proxy claims to set it: the same code path runs in local dev, in tests, and in any future non-Render environment, where nothing stops a direct caller from sending an arbitrary `Rndr-Id` value. Trusting a header's *content* because of who usually sets it, rather than validating that content regardless of source, is exactly the kind of assumption this CRITICAL REVIEW section exists to not make.

A `jakarta.servlet.Filter` (registered early in the filter chain) wraps every request:

```
String raw = request.getHeader("Rndr-Id");
String requestId = sanitize(raw);  // see below; null/invalid raw -> generates one
MDC.put("requestId", requestId);
response.setHeader("Rndr-Id", requestId);
try {
    chain.doFilter(request, response);
} finally {
    MDC.remove("requestId");
}
```

**Filter runs at highest precedence.** Registered with `Ordered.HIGHEST_PRECEDENCE` (e.g. via a `FilterRegistrationBean` with `setOrder(Ordered.HIGHEST_PRECEDENCE)`, or `@Order(Ordered.HIGHEST_PRECEDENCE)` on the filter bean itself) so it's the first thing that runs on the way in and the last thing that runs on the way out, relative to every other filter in the chain. The whole point of this filter is that `requestId` is in the MDC before *anything else* in the chain can log, and stays there until after everything else has finished — a filter registered at ordinary precedence could end up running after some other filter that logs something, leaving that earlier log line without a `requestId` for no good reason.

**Doc note for slice 5 and beyond: MDC does not propagate to other threads.** `MDC` is `ThreadLocal`-backed, so `requestId` is only visible to code running on the *same thread* this filter ran on. Slice 5's `CompletableFuture.allOf(...)`-based Apify calls run on different threads (whichever executor backs those futures) — log lines emitted from inside those async tasks will **not** automatically carry the `requestId` this filter set, even though they're logically part of the same request. When slice 5 is built, it must explicitly copy the context across: capture `MDC.getCopyOfContextMap()` on the calling thread before dispatching the async work, call `MDC.setContextMap(...)` at the start of each async task, and clear it when that task finishes. Not built in this slice, since there's no async work yet to carry it onto — stated here so slice 5 doesn't rediscover this gap the hard way.

**The `finally` block is load-bearing, not decorative.** `MDC` is backed by a `ThreadLocal`, and application servers (Tomcat included) reuse worker threads across requests from a pool — if `MDC.remove` only ran on the happy path, a request that throws would leave its `requestId` sitting in that thread's `ThreadLocal`, ready to silently attach itself to whatever unrelated request the pool hands that thread next. The `finally` guarantees cleanup on every exit path, including an uncaught exception propagating out of `chain.doFilter`.

**Sanitization, since an inbound header is untrusted input:**
- **Generated server-side by default.** If no `Rndr-Id` header is present, a fresh UUID is generated — this is the common case and needs no validation.
- **If a header value is present, it's sanitized before anything else touches it:**
  - **Length-capped.** A UUID is 36 characters; cap accepted length well above that (e.g. 64 characters) to allow other reasonable ID formats some callers might send, but reject anything grossly oversized — an unbounded header value is itself a resource-exhaustion vector (a client sending a multi-megabyte header value), independent of what it does to a log line.
  - **Charset-restricted.** Only `[A-Za-z0-9-]` accepted (matching typical ID shapes, including UUIDs) — this is what directly defeats a log-injection attempt: a header value containing `\n`, `\r`, or other control characters could otherwise forge what looks like a second, fake log line/field inside a single real one. Rejecting anything outside this charset closes that off at the source, not by trying to escape dangerous characters after the fact.
  - **A value that fails either check is never used, in any form.** The filter falls back to generating a fresh UUID instead — it does **not** truncate the bad value and use the truncated remainder, does **not** strip the bad characters and use what's left, and critically does **not** let the raw rejected value reach a log line "for debugging" (e.g. logging `"rejected invalid requestId header: <raw value>"` would just relocate the injection into a different log line). The failure is silent to the attacker (they get a normal response with a server-generated `Rndr-Id`, no error indicating their header was rejected) but never silent in the sense of "the bad value quietly made it into a log somewhere" — it provably never does, because it's never referenced again after the validation check fails.
- **Returned as a response header**, `Rndr-Id`, carrying whichever value is actually in effect (the client's own, if it passed validation, or the freshly generated one if it didn't or if none was sent) — so a caller can always correlate their request against server-side logs using the value Spring Boot actually used, not assume their own header round-tripped unchanged.

## 3. The startup guard's existing log lines, in the new format

The guard (slice 2) runs before any HTTP request exists, so its INFO/ERROR lines never carry a `requestId` — nothing in this slice changes that, and nothing needs to.

**`StartupGuardTest`'s existing assertions should still hold, unchanged — verified, not assumed.** `assertErrorLogLine` (and the plain `.contains("INFO")`/`.contains("ERROR")` checks on the happy-path tests) are substring checks against the raw captured output line, not checks anchored to the old bare-Logback-default console pattern. Under `ecs` format:
- `"ERROR"` / `"INFO"` still appear verbatim as the `log.level` field's string value.
- The logger's simple name (`StartupGuardBeanFactoryPostProcessor`) still appears as a substring of the `log.logger` field's fully-qualified value.
- Every property/environment/mode substring the tests check for (`"STAGING"`, `"app.bachs.base-url"`, etc.) still appears verbatim inside the `message` field's JSON-escaped string value, since those come from the same `log.info(...)`/`log.error(...)` calls in `StartupGuardBeanFactoryPostProcessor.java`, completely unchanged by this slice.

This gets confirmed by actually running the existing `StartupGuardTest` suite once `logging.structured.format.console=ecs` is set, in GREEN — not just reasoned through here. **If any assertion breaks, the plan is to fix the assertion to match the new (still-correct) format, with a comment explaining why, rather than loosen the format choice to avoid touching the test.** Expectation going in: none should break, per the reasoning above, but this gets proven, not assumed.

## 4. One access log line per request, logged in the filter's `finally` block

One line per request, emitted from the same filter, in the same `finally` block that clears the MDC (logged *before* the clear, so the line still carries its own `requestId` via the MDC-inclusion mechanism from Section 1) — fields: HTTP method, path **without the query string**, response status, duration in milliseconds, and `requestId` (automatic, via MDC).

- **Path without query string**: `request.getRequestURI()`, not `request.getRequestURL()` and not any manual string surgery on the latter — the servlet API already gives the path alone, with the query string (if any) available separately via `getQueryString()` and deliberately never read by this code at all. There's no "strip the query string" step to get wrong, because the query string is never in hand to begin with.
- **Status**: `response.getStatus()`, read after `chain.doFilter(...)` returns (or throws — see below), since the status isn't known before the downstream handler has run.
- **Duration**: measured with `System.nanoTime()` at entry and exit, not the project's injected `Clock`. This is a deliberate, narrow exception to CLAUDE.md's "time comes from an injected Clock" rule, stated explicitly rather than silently done: that rule exists for business-logic correctness and testability of wall-clock timestamps and deadlines (so tests can control *what time it is*). Measuring elapsed duration for an access log line is a different problem — `System.nanoTime()` is monotonic and immune to wall-clock adjustments (NTP sync, manual clock changes) during the request, which an injected `Clock.instant()`-based before/after subtraction would not be. For this specific purpose, `nanoTime()` is the more correct tool, not a workaround to avoid wiring a `Clock` through a filter.
- **Logged in `finally`, after the exception-path case too**: whether the request completed normally or the downstream threw, this line still gets logged — status comes from whatever `response.getStatus()` reports at that point (likely a 5xx if an unhandled exception reached the container's default error handling before this filter's `finally` ran, though the exact status in that case depends on container behavior and isn't pinned down further here).

**Test: a secret in the query string never appears in any log line.** Request a path like `/some/path?token=supersecret123` through the filter; assert the captured output's access-log line contains the path (`/some/path`) but not the query string or the secret value, and — more strongly — assert `supersecret123` appears *nowhere* in the entire captured output for that request, not just absent from the one access-log line. This is what actually proves the query string was never read, rather than merely not being printed by one specific line while some other code path leaks it.

## 5. Failure tests, written first

1. **Forged header: embedded newline.** `Rndr-Id: abc\ndef` (or the HTTP-layer-safe equivalent a test can actually send — most HTTP clients/servers reject a raw `\n` in a header value before it reaches application code at all, so this test may need to go through the filter directly with a crafted `HttpServletRequest` mock rather than a real HTTP round-trip, to actually exercise the sanitization logic rather than relying on a lower layer to have already blocked it). Assert: the filter generates a fresh UUID instead, the response's `Rndr-Id` header is that fresh UUID (not the forged value, not even a truncated/escaped version of it), and the captured log output for that request contains neither the literal forged value nor any sign of a second, injected-looking log line.
2. **Forged header: very long value** (e.g. 10,000 characters). Same assertions as above — generates fresh, response header is the fresh value, log output never contains the oversized value.
3. **requestId does not leak across requests on a reused thread.** Simulate two sequential requests through the same filter instance on the same thread (e.g. call the filter's `doFilter` twice in a row within one test method, with two different mock request/response pairs, both referencing the same thread by construction since JUnit runs the test method on one thread) — assert the second request's captured requestId is different from the first's, and specifically that it is **not** the first request's value accidentally surviving in the `ThreadLocal`.
4. **requestId is still present and logged on an exception path.** A filter chain where the downstream handler throws — assert `MDC.get("requestId")` is non-null and matches what the filter set *while the exception is propagating* (so a log line emitted during exception handling still carries it), and assert `MDC.get("requestId")` is `null` again immediately after `doFilter` returns (via the exception) — proving the `finally` cleanup ran even on this path, which is also what prevents test case 3's leak scenario from happening after an error, not only after success.
5. **A secret in the query string never appears in any log line** (Section 4) — request a path with a `?token=...`-shaped query string through the filter, assert the secret value is absent from the entire captured output, not just from the access-log line specifically.
6. **A real log line, parsed, has the requestId as a JSON field with the generated value.** Boot the real application (or a minimal slice of it sufficient to exercise the filter against a real request), capture stdout, parse the resulting line(s) with an actual JSON parser (not a substring check), and assert the parsed object's `requestId` field equals the value the filter generated for that request — proving the MDC-to-JSON-field mechanism actually works end to end, not just that the right substring happens to appear somewhere in the raw text.
7. **The real application, with structured logging enabled, produces a valid JSON startup guard line with `message`, `level` (or the format's equivalent key name — `log.level` under `ecs`), and `logger` fields.** Boots the real app with `logging.structured.format.console=ecs` actually set (not a hand-built test context that bypasses `application.properties`), captures the startup guard's own INFO line, parses it as JSON, and asserts those three fields are present and correctly populated — the counterpart, at the JSON-structure level, to Section 3's substring-level reasoning about why the existing `StartupGuardTest` assertions should keep passing.

Every one of these asserts the actual log output (via `CapturedOutput`, same pattern as `StartupGuardTest`), not just the in-memory MDC state — the point is proving what a log line actually contains, since that's the thing an operator or an attacker would actually see.

## 6. Never logged: wallet address, Bachs URLs, secrets, request bodies

This slice introduces no new path that would log any of these — `extractedWallet` doesn't exist as a concept until slice 6 (cleaning pipeline) populates it, there's no request-body logging anywhere in this app, and the Bachs-URL-redaction discipline already established in slice 2 (`StartupGuardTest` asserting `output.getAll()).doesNotContain(FAKE_SANDBOX_URL)` etc.) is untouched by this slice's changes. Section 4's access-log line is the one new place a secret *could* have leaked (via the query string) and is specifically tested against that (failure test 5 above).

**Where real redaction infrastructure would live, if it's ever needed beyond "just don't pass it as a log argument":** Spring Boot's structured logging support allows a fully custom formatter via `logging.structured.format.console=<fully-qualified-class-name>` implementing `StructuredLogFormatter<ILoggingEvent>` — a custom formatter could inspect and mask specific field values (e.g. a field literally named `extractedWallet`) before serialization, as a backstop beyond "the code that logs things is disciplined about what it passes." That's not built in this slice — CLAUDE.md's existing rule ("Never log or return extractedWallet. Redact before logging at every level") is enforced today, and will keep being enforced going forward, by the same discipline-plus-test-assertion pattern already used for the Bachs URLs: never pass the sensitive value as a log argument in the first place, and assert its absence from captured output in whichever test exercises the code path that touches it. A structured-formatter-level backstop is a reasonable future hardening step once there's an actual `extractedWallet`-touching code path to protect (slice 6+), not something to build speculatively now against a value that doesn't exist yet.
