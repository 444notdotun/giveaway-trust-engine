Verified directly against X's own developer docs (fetched the actual pages, quoted verbatim below rather than paraphrased from memory):
- Authorization endpoint: `https://x.com/i/oauth2/authorize`
- Token endpoint: `https://api.x.com/2/oauth2/token`
- PKCE (`code_challenge`/`code_challenge_method`) is required, not optional, for this flow.

**Scopes — quoted from X's own docs, not assumed.** The full documented scope list (`docs.x.com`, OAuth 2.0 authorization-code page) includes, among others: `"users.read | Any account you can view, including protected accounts."` and `"users.email | Email from an authenticated user."`. Separately, the **user-lookup endpoint itself** (`GET /2/users/me` — the call this flow actually makes to learn who just logged in) documents its own required security as `"OAuth2UserToken: [users.read, tweet.read]"` in its OpenAPI spec — i.e. that specific endpoint requires **both** `users.read` and `tweet.read` together, not `users.read` alone. **Scopes requested: `users.read tweet.read`.** `users.email` is **dropped** per your instruction to not request it unless the PRD needs it — grepping the PRD for every mention of `email` found exactly one: the bare field listed in the domain model (Section 3). It is never read, displayed, or sent anywhere else in the entire document. The PRD does not need it. No `offline.access` requested — this app only needs one-time identity at login, not ongoing access to the CM's X account, so there's no reason to ask for continued access.

**X API access tier required: not confirmed, flagging rather than guessing.** I checked `docs.x.com/x-api/getting-started/about-x-api`, its access-levels anchor, and `docs.x.com/x-api/getting-started/pricing` — none of them state which tier (Free/Basic/Pro) `GET /2/users/me` or OAuth 2.0 login requires; they describe pay-per-usage credit pricing, not tier gating for this specific endpoint. This needs confirming directly against your X Developer Portal account (or X's support) before relying on it working at whatever tier the app's X Developer account is currently on — not something I can verify further from the docs alone.

**What happens if X is down, times out, or rate-limits the login attempt?** Both outbound calls (token exchange, user lookup) carry explicit connect and request timeouts (Section 6). No automatic retry is built for either — unlike Apify's own client-level retries (PRD Section 11), which exist for a backend-initiated pipeline call with no human waiting; a login is an interactive, human-initiated action, so the CM clicking "log in" again **is** the retry mechanism. A timeout, 5xx, or 429 from either call surfaces immediately as a clean login failure (no stack trace, no partial state — Section 5's failure tests cover exactly this: no half-created `community_manager` row).

Flow: redirect CM to X's authorize URL with `code_challenge`/`state` → X redirects back to our callback with `code`/`state` → server verifies `state`, retrieves the matching `code_verifier` (below), exchanges `code` + `code_verifier` for an X access token via the token endpoint → server calls `GET /2/users/me` with scopes `users.read tweet.read` to get `{id, username}` → upsert `community_manager` keyed on `x_user_id` → issue our own access + refresh token pair (Section 2) → set cookies (Section 3) → respond (see "no frontend yet" below). **X's own access/refresh tokens are discarded immediately after the user-lookup call returns — never persisted anywhere (DB, Redis, or logged), since this app has no further use for them** (failure test in Section 5 asserts this directly).

**The redirect URI sent to X comes from config (`app.x-oauth.redirect-uri`, bound from `X_OAUTH_REDIRECT_URI`), never built from the inbound request's `Host` header.** Stated explicitly as a guarantee, not left as an implicit assumption a future refactor could quietly break: deriving a redirect/callback URL from a client-controlled header is a known open-redirect/host-header-injection shape, and the whole point of registering a fixed callback URL with X is that X itself enforces it must match exactly — building it dynamically from the request would both defeat that enforcement and introduce a new untrusted-input path this slice doesn't otherwise have.

**Callback path, fixed by the already-committed RED tests:** `/auth/callback` (login-initiation at `/auth/login`), no trailing slash — `OAuthLoginFlowTest`'s `callback(...)` helper already hits exactly this path. Staging's registered callback URL (and `X_OAUTH_REDIRECT_URI`) is therefore `https://giveaway-trust-engine.onrender.com/auth/callback`; the local equivalent is `http://127.0.0.1:8080/auth/callback` (or whatever port `PORT` is overridden to locally).

**Hand-rolled, not Spring Security OAuth2 Client.** This is two outbound HTTPS calls (token exchange, user lookup) using `java.net.http.HttpClient` with explicit connect timeouts **and** explicit request/response timeouts (both calls, not just connection establishment — the same connect-vs-command distinction Section 1 draws for Redis applies here: a slow X response after a successful connection is a different failure mode from never connecting at all, and both need their own bound) — consistent with how this project already makes outbound HTTP calls (no Apify/Bachs SDK dependency added either; CLAUDE.md's "every external call has an explicit timeout" applies here identically). Pulling in `spring-security-oauth2-client` would mean adopting all of Spring Security for a two-call flow; not proposed.

**No transaction or row lock is held across either call.** The `community_manager` upsert (a DB write) only happens *after* both X calls have already returned successfully — never inside a transaction that's also waiting on X's network round-trip. This is the same rule already enforced elsewhere in this codebase (CLAUDE.md: "never hold a transaction or row lock across an external call") applied to a new external dependency; the upsert's own transaction is short, local, and entirely after the point where X could still be slow or down.

**PKCE `code_verifier` and `state`: stored server-side in Redis, short TTL — not in a cookie, and here's why `SameSite=Strict` cannot work for this specific hop.** The callback request (`X redirects back to our callback`) is a **cross-site, top-level navigation** originating from `x.com` — exactly the kind of request a `SameSite=Strict` cookie is designed to withhold (Strict cookies aren't sent on *any* cross-site request, including a top-level redirect from another origin; only `Lax` permits a cross-site top-level `GET` navigation to carry a cookie). The session cookies set after login succeeds (Section 3) stay `Strict` — they're never involved in a cross-site hop, since every request that uses them originates from this app's own frontend. The OAuth state is a different, earlier, one-time problem: nothing cookie-based set before the redirect to X can reliably be read back on X's redirect into our callback without weakening to `Lax` specifically for that one value. Rather than carve out a `Lax` exception cookie, this app stores `{state → codeVerifier}` **server-side in Redis** (`oauth:state:{state}`, TTL 10 minutes, deleted on first successful read — single use, matching the PKCE value's own single-use nature) — no cookie at all is needed to carry the verifier across the redirect, which sidesteps the `SameSite` question entirely rather than resolving it with a weaker cookie policy. If Redis is unreachable at the moment a CM starts a login, the login attempt fails cleanly (same category of failure as any other Redis-down path in this slice) rather than silently falling back to a cookie.

**No frontend exists yet — the callback response reflects that honestly, rather than assuming one.** On success, the callback responds directly (minimal body — e.g. a short confirmation) with the session `Set-Cookie` headers attached; it does **not** redirect to a frontend route, because there is no frontend route to redirect to. **Open items for whenever a frontend exists** (not decided now, since deciding them without a real frontend to decide them against would be guessing): the frontend's domain layout (same origin as the API, or a separate domain — this determines whether the session cookies even need `SameSite=Strict` reconsidered, and whether CORS matters at all); and a redirect allow-list (once the callback *does* redirect post-login, the target must be validated against a fixed allow-list of known frontend URLs, never an open redirect to an arbitrary caller-supplied `return_to` value).

**Schema finding, now folded into this slice's PRD-sign-off scope (header):** `community_manager` currently has no immutable X identifier — only `x_handle` (mutable; X allows handle changes) with a `UNIQUE` constraint. X's user-lookup response carries both an immutable numeric `id` and the mutable `username`. Upserting by `x_handle` means a CM who renames their X handle gets a **second, disconnected `community_manager` row** on their next login, orphaning their existing giveaways/quota under the old handle. **Proposed fix: migration `V2` adding `x_user_id text NOT NULL UNIQUE` to `community_manager`, upsert keyed on `x_user_id`, with `x_handle` refreshed (not re-keyed) on every login to stay current** (Section 5 tests this directly — a simulated handle rename must update the same row, not create a new one).

**`email`: dropping the scope means this app can no longer populate it from X at all.** `community_manager.email` is currently `NOT NULL` and `UNIQUE` in the schema, but (per the grep above) the PRD never actually uses the `email` field for anything. Since `users.email` is deliberately not requested, there is no source for this column's value at login time at all — not "sometimes missing," but **never populated by this flow, ever.** This needs the same migration (`V2`) to make `email` nullable — **a separate PRD wording question, not covered by the Section 11/9/3 approval above and still open** (Open items 5a): the PRD's own domain model lists `email` as a plain field with no stated nullability, and this slice is changing that. **No placeholder/synthesized email is written** — a fabricated value would collide with the column's own `UNIQUE` constraint the instant two such logins happened, and would be misleading data to anyone who later reads it.

## 2. Tokens

**Access token: JWT, HS256, 15 minutes.** Claims: `sub` (cmId), `familyId`, `iat`, `exp` (`iat` + 15 min, computed from the injected `Clock`, never `Instant.now()`). No `jti` — access tokens aren't individually revocable (only by familyId, via the Redis set that future resolve endpoints will check), so there's nothing a per-token identifier would let us do differently.

**Nimbus JOSE+JWT (`com.nimbusds:nimbus-jose-jwt`) — approved by Adedotun on 2026-10-23, Open item 3 CLOSED.** This project had no JWT library through chunks 1–4 of the build; `JwtService` was deliberately hand-rolled HS256 in the interim (constant-time signature comparison, `alg` pinned before any signature check — the same properties Nimbus itself provides), as an explicit, acknowledged, temporary deviation while this approval was pending, not a silent abandonment of the proposal below. As of the chunk 4 review, `JwtService`'s internals now use Nimbus; its public API (`issueAccessToken`, `verifyAccessToken`) is unchanged.

**Version actually pinned: `10.10`, not the `10.4` first proposed here.** The original reasoning below (Spring Security 7.0.3's own POM) found `10.4` at the time this section was first written; by approval time, Maven Central's own `maven-metadata.xml` showed `10.10` as current stable, six releases past `10.4` — verified directly, not assumed stale or current without checking. Also verified against Snyk at approval time: zero open vulnerabilities for `10.10`. One historical CVE exists for this library (CVE-2025-53864, a DoS via uncontrolled recursion when parsing a deeply-nested JSON claim set) but was fixed in `10.0.2`, well below this pin. Pinned explicitly in `pom.xml`, not deferred to any BOM — confirmed separately that Spring Boot 4.1.1's own BOM does not manage this coordinate at all (`grep -i nimbus` against the locally-cached `spring-boot-dependencies-4.1.1.pom` returns nothing; it's only pulled in transitively through `spring-security-oauth2-jose`/`-resource-server`, neither of which this project depends on).

**Verification pinned to one algorithm, not trusted from the token's own header.** `JwtService.verifyAccessToken` parses the token via Nimbus's generic `JWTParser.parse` (not `SignedJWT.parse` directly) specifically so the `alg` check runs BEFORE committing to signed-JWT handling: a token asserting `alg: none` parses as a `PlainJWT` and is rejected at that same check, as is any other signed algorithm (RS256, HS384, ...) or an encrypted JWT — none of them are ever routed to a different verification strategy; `HS256` is the only value this class treats as valid, checked before any verifier is even constructed. This is the specific property the algorithm-confusion failure test (Section 5) exists to prove. `exp`/`iat` are checked against the injected `Clock`, never Nimbus's own default-clock helpers. Malformed claims (`sub`/`familyId` missing or not a parseable UUID) are caught defensively and surfaced as a `malformed-claims` reason — never an uncaught exception reaching the servlet filter as a raw 500.

**Signing key: environment variable, no default, minimum length enforced at startup — rule stated precisely, not left implicit.** New `JWT_SIGNING_KEY` Render variable (see Section 1's list — this one is new, not yet declared anywhere). **`app.jwt.signing-key` is interpreted as base64, decoded to raw bytes, and the 32-byte minimum is enforced against the *decoded* byte length — not the length of the configured string itself.** `JWT_SIGNING_KEY`'s real value is the output of `openssl rand -base64 48` — a 64-character base64 string encoding 48 raw random bytes. Measuring the configured *string's* length would overcount: base64's alphabet carries 6 bits of entropy per character, not 8, so a string-length check would accept a value that's actually short on real entropy once decoded. Decoding first and measuring the real byte count is the standard, correct way to size key material that arrives base64-encoded, and it's what this app's own HMAC-SHA256 signing will consume as key bytes either way, so the length actually enforced is the length actually used to sign.

**Failure mode if the configured value isn't valid base64 at all:** refuse to start, naming `app.jwt.signing-key`, same as any other invalid value — no silent fallback to treating it as raw UTF-8 bytes instead. One interpretation, applied consistently, never two competing readings of the same property.

A new `JwtSigningKeyGuardBeanFactoryPostProcessor`, same pattern as the existing `StartupGuardBeanFactoryPostProcessor` (slice 2): refuses to start if the key is missing/blank, contains `${`, isn't valid base64, or decodes to fewer than 32 bytes (256 bits — the minimum HMAC-SHA256 key length security guidance actually calls for, not an arbitrary round number). A separate guard class, not folded into the existing one, since each guard enforces one orthogonal invariant and slice 2's guard is already named and scoped around Bachs/environment — mixing concerns there would make a future failing assertion ambiguous about which invariant actually broke.

**Tests must prove the exact boundary, not just "short keys fail":** a base64-encoded value that decodes to exactly 31 bytes is refused; a base64-encoded value that decodes to exactly 32 bytes is accepted. Off-by-one on this boundary is exactly the kind of bug a vaguely-worded "shorter than 32 bytes" assertion would miss.

**Refresh token: NOT a JWT — an opaque, split identifier+secret value, 7 days, single-use, stored hashed.** The existing `refresh_token` table (`token_id`, `family_id`, `cm_id`, `used`, `expires_at` — from slice 1's migration, unchanged) already has the right shape for the identifier half; it has no column for a secret or its hash yet. **New migration (`V2`, alongside the `x_user_id` addition above) adding `token_hash bytea NOT NULL`** — SHA-256 of a freshly generated high-entropy random secret (32 random bytes), never the secret itself. SHA-256, not bcrypt/Argon2: those algorithms exist to slow down brute-forcing a *low-entropy* human-chosen secret (a password); this secret is 256 bits of CSPRNG output with no feasible brute force regardless of hash speed, so a slow KDF would only cost latency with no real security benefit.

The value actually set in the refresh cookie is `base64url(tokenId) + "." + base64url(secret)`. On refresh: split on `.`, look up the row by `tokenId`, compare `SHA-256(secret)` against the stored `token_hash` (constant-time comparison — `MessageDigest.isEqual`, not `Arrays.equals` or `.equals()`, to avoid a timing side-channel on the hash comparison itself). `tokenId` alone is never sufficient to refresh; the secret must also match.

**Rotation.** A successful refresh: an atomic conditional `UPDATE refresh_token SET used = true WHERE token_id = :id AND used = false` (the same atomic-conditional-UPDATE pattern this codebase already uses for quota claiming — CLAUDE.md: "money and quota math happens in SQL, never read then write in Java" — token single-use consumption is the identical race shape, so the identical fix applies) returning the affected row count, then — only if that update affected exactly one row — insert a new `refresh_token` row in the same `familyId` with a freshly generated `tokenId`/secret/hash and a new 7-day expiry, and issue a new 15-minute access token. **This is also the mechanism the concurrent-refresh failure test (Section 4) exercises directly**, not a separate code path invented just for that test.

**All time from an injected `Clock` — corrected: no such bean exists yet anywhere in this codebase.** Checked directly (`grep -rl Clock src/main src/test` returns nothing) rather than assumed — CLAUDE.md's "time comes from an injected `Clock`" rule has had nothing to apply to until now, since no prior slice's business logic needed to compare against the current time. **This slice adds the first one**: a single `@Bean Clock clock() { return Clock.systemUTC(); }`, and every time-dependent computation here (`issuedAt.plus(Duration.ofMinutes(15))`, `issuedAt.plus(Duration.ofDays(7))`, `clock.instant().isAfter(expiresAt)`) goes through it — no `Instant.now()` anywhere in this slice's code.

- A failure test proving reuse detection end-to-end through the real HTTP route (the component-level proof already exists in `RefreshTokenConcurrencyTest`, but — same honesty standard as Section 4's "honest scope boundary" for the revocation checker — the first slice that builds this route should re-prove it against the real endpoint, not just trust the component-level test transitively).

**`__Host-` cookie prefix: evaluated, not adopted.** The `__Host-` prefix requires all three of: `Secure` present, `Path=/` exactly (no other value permitted), and no `Domain` attribute. Checked against both cookies as they now stand:
- **Refresh cookie: incompatible, directly.** This fix (item 3) scopes it to `Path=/auth/refresh` specifically — `__Host-` mandates `Path=/` and nothing else, which would undo the exact scoping this fix exists to add. Adopting `__Host-` here would mean choosing between the prefix and the path-scoping; path-scoping wins, since it's the control that actually reduces this cookie's exposure to the other ~zero other things reading it.
- **Access cookie: compatible on paper, not adopted now.** `Path=/`, `Secure`, no `Domain` are already true today, so `__Host-` could be added here without changing anything else about it. Not adopted in this round simply because it wasn't asked for and is a separate, independent decision from the three fixes actually requested — flagging it as available, not doing it speculatively.
- **Local dev over `http://127.0.0.1` / `http://localhost`: not the actual blocker.** `Secure` cookies are rejected by browsers only on origins that aren't "potentially trustworthy" — both `localhost` and the entire `127.0.0.0/8` block are treated as potentially trustworthy by Chrome and Firefox regardless of scheme (per the Secure Contexts spec), so `Secure` cookies already work in this app's local dev setup today (confirmed by every existing cookie-flag test passing against the real local Testcontainers-backed app, which runs over plain `http://localhost`). `__Host-` adds no further restriction beyond what `Secure` already implies, so local dev was never going to be what rules it out — the `Path=/auth/refresh` requirement is.

## 4. Revocation: database first, then Redis — CRITICAL REVIEW

**Reuse detection.** A refresh request whose conditional `UPDATE ... WHERE token_id = :id AND used = false` affects **zero** rows means one of two things: the token was already consumed by a legitimate prior rotation (this *is* the reuse case — a copy of an already-rotated token is being replayed), or the token never existed / was already revoked. Either way, the response is the same: **revoke the entire family.** `UPDATE refresh_token SET used = true WHERE family_id = :familyId` (idempotent — re-running it against an already-fully-revoked family changes nothing and is harmless, which matters because a revoked family being hit again, e.g. by an attacker retrying, must not do anything worse the second time).

**Ordering: database write commits first, Redis write second — and this is deliberate, not incidental.** The database is the durable, authoritative revocation record; Redis is a 15-minute, fast-path cache that exists only so a future resolve endpoint doesn't have to hit Postgres on every call to check a condition that's almost always false. If the DB write happens first and commits, the revocation is real and permanent regardless of what happens to the Redis write next. If the Redis write then fails (Redis down, timeout), **the refresh/reuse-detection response to the caller is unaffected** — it already reflects a durably-revoked family. The gap this leaves (an already-issued, not-yet-expired access token in that family could still pass signature+expiry checks against an endpoint that *doesn't* consult Redis) is accepted and bounded: per PRD Section 15, only resolve endpoints check the revoked set at all, and resolve endpoints are specified to **fail closed with 503 whenever Redis is unreachable** — so if Redis is down, no resolve endpoint succeeds anyway, revoked-family or not. The one case this ordering is actually protecting against is the reverse: writing to Redis first and then having the DB write fail/roll back would leave a family temporarily looking revoked in the 15-minute cache while the authoritative store never recorded it — a transient, inconsistent state with no correctness benefit over doing it the other way around.

**The Redis structure: one key per `familyId`, not a single shared Set.** PRD's phrase "revoked set" is colloquial, not a literal Redis data-structure name. A single Redis Set (`SADD`) can't give each member its own independent TTL — `EXPIRE` applies to the whole key. Since each family's revocation needs its own independent 15-minute window starting from when *that* family was revoked, the actual structure is `SET revoked:{familyId} 1 EX 900`, checked with `EXISTS revoked:{familyId}` — satisfying CLAUDE.md's "every Redis key has a TTL" literally, per key, rather than one shared key whose TTL would reset or apply incorrectly across unrelated families.

**`RevocationChecker` component, built now, consumed later.** A small component with `isFamilyRevoked(familyId): boolean`, reading the key above, with an explicit connect+command timeout (Section 1) — on any Redis failure (timeout, connection refused), it throws a dedicated `RevocationCheckUnavailableException` rather than defaulting to `false` (which would silently fail open) or `true` (which would needlessly lock out every CM on a Redis blip). A `@ControllerAdvice` maps that exception to `503`, built now so every future resolve endpoint gets this behavior automatically just by calling `isFamilyRevoked(...)`, with no per-endpoint boilerplate to get right or forget.

**Honest scope boundary, carried forward:** no resolve endpoint exists yet (first one arrives in a later slice). This slice proves the `RevocationChecker` → `503` path at the component/exception-mapping level (Section 5's Redis-down failure test), the same way slice 2a left its three staging failure cases honestly marked "not yet demonstrated end-to-end" rather than fabricated against infrastructure that didn't exist. The first slice that adds a real resolve endpoint should re-prove this against that actual endpoint, not just trust this slice's component-level proof transitively.

**Which endpoints consult Redis at all, and the maximum window a revoked access token still works, per endpoint class — stated precisely, not hand-waved:**

| Endpoint class | Consults Redis? | Max window a revoked access token still works |
| --- | --- | --- |
| Resolve endpoints (not yet built) | Yes, every call (PRD Section 15) | **0** — every call re-checks the revoked set, so once the Redis write for that family has landed, the very next resolve call sees it. |
| Resolve endpoints, if the Redis *write* for this family's revocation failed after the DB commit (Section 4's ordering gap) | Yes, but the key for this family was never created | **Up to 15 minutes** — the access token's full fixed lifetime. The read itself succeeds (Redis is up), it just finds nothing for this specific family, so the endpoint proceeds as "not revoked" until the token expires on its own. This is the gap the DB-first ordering already accepts (above) — bounded by the token's own lifetime, never indefinite. **Observable, not silent**: this exact failure logs one WARN line naming the `familyId` (never a token or secret) and increments a Micrometer counter, so an operator can actually see this residual-window event happening, rather than it only existing on paper in this table. The reuse-detection caller that triggered the revocation (Section 2/chunk 3) still returns the same generic rejection to the client either way — whether the Redis write succeeded or failed is never distinguishable from the outside, since leaking that distinction would tell an attacker something about internal state they have no legitimate reason to know. |
| All other authenticated endpoints (Create giveaway, CSV export, List my giveaways) | **No, never** — this is PRD's own explicit design (Section 9: "at the cost of one Redis read **per resolve call**"), not a gap this slice introduces | **Up to 15 minutes**, always, by design — stated here so it's visible as a known, PRD-stated risk window rather than rediscovered later as a surprise. |

## 4a. Redis data loss within the revocation TTL window — accepted risk, scope-cut

**Built, reviewed, then cut.** A revocation-epoch mechanism (`SET revocation-epoch <now> NX`, consulted whenever the direct `revoked:{familyId}` key was absent, rejecting any token whose `iat` predated the epoch) was implemented, mutation-tested, and passing — then deliberately removed as a scope reduction after review. `RevocationChecker.isFamilyRevoked` now checks only the direct evidence: `EXISTS revoked:{familyId}`. Nothing else.

**The accepted risk this reintroduces, stated precisely:** Upstash (or any Redis) can lose all of its data — a restart, an eviction, an operator-triggered flush — and come back up reachable, authenticating fine, just **empty**. If that happens to coincide with the still-valid 15-minute window after a specific family's revocation, the direct evidence for that one revocation is gone, and `isFamilyRevoked` for that family now returns `false` — indistinguishable from "never revoked." Without the epoch fallback, there is no detection and no correction for this specific case.

**Why this is still bounded, not open-ended:** the risk is scoped to exactly the same 15-minute window already documented in Section 4's windows table for "the Redis *write* failed after the DB commit" — this is the same shape of gap (a revocation whose Redis-side evidence never existed or didn't survive), not a new or larger one. The underlying access token is still fixed at a 15-minute lifetime regardless of what Redis remembers; once that token's own `exp` passes, the gap closes itself, with or without Redis's help. The **database** side of the revocation (every `refresh_token` row in the family marked `used = true`) is unaffected by any Redis data loss and remains the authoritative record — a subsequent *refresh* attempt against any token in that family still correctly fails (Section 2's single-use/reuse logic reads from Postgres, not Redis). This gap is specific to a **resolve endpoint** checking a **still-live access token** during that exact narrow window; it does not let a stolen refresh token be used again, and it does not persist past the access token's own expiry.

**What this means in practice:** during a Redis data-loss event, any access token issued in the 15 minutes immediately before a revocation that hadn't yet had its Redis evidence read back (or whose evidence was lost before being read) could pass a resolve endpoint's revocation check as "not revoked" for up to the remainder of that token's 15-minute lifetime. This is accepted as a known, bounded risk rather than engineered around, in exchange for not carrying the epoch mechanism's own complexity (an extra Redis key, a sliding TTL, a second code path in every check) for a failure mode this narrow.

**Accepted difference: reuse-detection timing vs. unknown-token timing.** The reuse path (`atomicallyConsumeAndRotate` loses its race, or a token is presented a second time after rotation) takes a different, slower route than the unknown/malformed-token path: it makes a synchronous `revokeFamily` call (a DB `UPDATE` across the whole family, then a Redis `SETEX`) before throwing the same generic rejection message. An unknown or malformed cookie value never reaches that code — it fails the lookup or the decode step and throws immediately. The two paths are therefore distinguishable by response time, not just by the identical exception message and body. This is accepted, not fixed, because reaching the reuse path at all requires already possessing a valid, previously-issued 32-byte secret whose hash matches a real `refresh_token` row — an attacker who does not already hold a legitimate token has no cheap way to trigger the slower path, so the timing side-channel does not help an attacker who is only guessing or probing.

**Production readiness item: no cleanup of expired `refresh_token` rows.** Nothing in this slice prunes `refresh_token` rows once `expires_at` has passed; both used and unused expired rows accumulate indefinitely. This is correct and safe (expiry is still enforced on read, at the strict boundary described above) but is a storage-growth and index-bloat concern over time. A periodic cleanup job (e.g. a scheduled `DELETE FROM refresh_token WHERE expires_at < now() - <retention>`) is needed before production but is out of scope for this slice.

**Production readiness item (chunk 4 review): rate limiting on `/auth/login` and `/auth/callback`.** Neither endpoint has any rate limiting today. Each real `/auth/login` call writes to Redis (`SETEX`); each real `/auth/callback` call does at least one Redis `GETDEL` and, past the binding-cookie check, two outbound HTTPS calls to X. Upstash's free/low tiers meter and cap commands per month (Section 1 notes the free-tier constraint pattern this project already lives with for Render/Supabase) — an unthrottled flood of `/auth/login` calls (even ones that never complete a real login) could exhaust that command quota well before any legitimate traffic does, taking down every *other* feature that depends on Redis (revocation checks, resolve endpoints) as collateral damage, not just OAuth. Needed before production: a rate limit on both routes (by source IP at minimum), sized against whatever Upstash plan production actually runs on — not sized here, since that depends on a plan choice not yet made.

**Production readiness item (chunk 4 review): no revocation of X's own tokens after the user lookup.** This app already discards X's access/refresh tokens immediately after `GET /2/users/me` returns — never persisted, logged, or reused (Section 0, failure test 20). It does not, however, call X's own token-revocation endpoint to tell X that token is now dead on this app's side. X will let it sit until its own `expires_in` (seen in the token-exchange response, currently 7200 seconds per the test stubs) lapses naturally. This is low risk — the token never leaves this process's memory for the ~second it's alive here, so there's nothing for an attacker to intercept in practice — but an explicit revocation call would be the more defensively-complete posture (one fewer live credential outstanding, for no real cost beyond one more HTTP call this app already knows how to make). Not built now: optional hardening, not a gap this slice's own tests exercise.

## 5. Failure tests, written first — shown red before any implementation

1. **Two concurrent refreshes with the same token: exactly one wins, the other triggers reuse handling.** Two threads call the refresh path with the identical `tokenId`/secret at the same time; assert exactly one receives a new rotated token pair, the other receives the reuse-detected response, and afterward every token in that family has `used = true` in the database — proving the atomic conditional `UPDATE` actually serializes the race rather than both threads reading `used = false` and both proceeding.
2. **Reuse of a rotated token revokes the whole family.** Refresh once (rotates token A → token B, A now `used = true`). Present token A again; assert every token in the family (including B, not yet expired or used by anyone) is now `used = true`, and that a subsequent refresh attempt using B also fails.
3. **A revoked token is rejected.** After family revocation, any further refresh attempt against any token in that family fails — not just the originally-reused one.
4. **An expired access token is rejected** — signature valid, `exp` in the past (relative to the injected `Clock`, not wall-clock `Instant.now()`, so this test controls time deterministically rather than sleeping).
5. **A tampered signature is rejected** — flip one byte of a validly-issued token's signature segment; must fail verification, not fail at some later unrelated step.
6. **Algorithm confusion (`alg: none`) is rejected.** Hand-construct a token with header `{"alg":"none"}` and no signature segment, claiming a valid `cmId`/`familyId`; Nimbus's verifier must reject this outright because the library is configured to accept only `HS256` and never trusts the token's own `alg` header to pick a verification strategy — the exact class of bug a hand-rolled verifier would be likely to get wrong.
7. **Redis down gives 503, not 200 (or a silent fail-open).** Point `RevocationChecker` at an unreachable Redis (wrong port, or a Testcontainers Redis container stopped mid-test); assert `isFamilyRevoked(...)` throws `RevocationCheckUnavailableException`, and that the `@ControllerAdvice` mapping produces a `503` response, not a `200`/`401` that would mean "not revoked" or "revoked" respectively — either of which would be a wrong, Redis-outage-shaped guess instead of an honest failure.
8. **Cookie flags are asserted directly**, not assumed from code review: parse the real `Set-Cookie` header(s) from a real login/refresh response and assert `HttpOnly`, `Secure`, and `SameSite=Strict` are all literally present, for both the access and refresh cookies.
9. **`userId`/`cmId` always comes from the verified JWT, never from a request body or path parameter.** Craft a request whose body or path claims a different `cmId` than the one in the caller's own valid JWT; assert the JWT's `cmId` is what's actually used (there's no endpoint in this slice that varies behavior by a body/path-supplied `cmId` yet, so this is tested at the extraction-point level — the component that pulls `cmId` out of the authenticated request context never reads it from anywhere else — with a note that every future endpoint built on top of this must be reviewed to confirm it never introduces a body/path `cmId` field that silently shadows it).
10. **A connection over TLS with the correct password works** (Section 1) — a real `RevocationChecker` read against a TLS-and-auth-configured Testcontainers Redis succeeds end to end.
11. **A wrong password fails fast and fails closed.** Configure the client with an incorrect password against the same TLS-and-auth Redis; assert the failure surfaces within the configured timeout (not a hang), and maps to the same `503` `RevocationCheckUnavailableException` path as a network-level Redis outage — auth failure is still "can't trust an answer," not a different outcome.
12. **Neither the Redis password nor the full connection string ever appears in any log line**, on both the successful-TLS-connection path and the wrong-password failure path (Section 1) — the failure path specifically, since an exception message or stack trace is exactly where connection details could leak if not deliberately kept out.
13. **OAuth: missing or wrong `state` on the callback is rejected.** A callback request with no `state` parameter, or one that doesn't match any entry in Redis (Section 0), fails cleanly — never falls through to treating the request as if `state` had matched.
14. **OAuth: `state` replay is rejected.** Using a `state` value a second time (after its first, legitimate use already consumed and deleted the Redis entry) fails the same way a missing/wrong `state` does — proving the single-use delete-on-read actually happened, not just that a second use is coincidentally invalid for some other reason.
15. **OAuth: PKCE verifier mismatch is rejected.** A callback presenting a `code_verifier` that doesn't hash/transform (per PKCE's `S256` method) to the `code_challenge` originally sent to X's authorize endpoint fails the token exchange — proving this app's own PKCE handling is actually wired correctly, not merely trusting that X enforces it.
16. **OAuth: X's own callback error parameter is handled cleanly.** X redirects back with `?error=access_denied` (or any other documented error code) instead of `code` — e.g. the CM declined the authorization on X's own consent screen; this is a normal, expected outcome, not a crash or a 500, and produces a clean login-failure response.
17. **OAuth: an X timeout during token exchange or user lookup leaves no half-created `community_manager` row.** Simulate a timeout (WireMock delay past the configured timeout) on each of the two X calls in turn; assert no row was written to `community_manager` in either case — the upsert only ever happens after both calls have already succeeded, never attempted speculatively before they're known to have worked.
18. **OAuth: concurrent first-time logins for the same X user create exactly one `community_manager` row, not two.** Two simultaneous callbacks resolving to the same `x_user_id` (e.g. a double-click, or two tabs completing the flow close together); assert exactly one row exists afterward, enforced by the `x_user_id` `UNIQUE` constraint plus an insert-then-handle-conflict pattern (not a read-check-then-insert race).
19. **OAuth: a handle rename updates the same account, not a new one.** Log in once (creates a row keyed on `x_user_id`), then log in again with the same `x_user_id` but a different `username` in X's response (simulating a rename); assert it's the same `community_manager.id` as before, with `x_handle` updated to the new value — not a second row.
20. **OAuth: X's own tokens are discarded, not stored.** After a successful login, assert the X access token (and refresh token, if X issues one) returned by the token-exchange call appears nowhere — not in any database table, not in Redis, and not in any captured log line.
21. ~~Redis restart losing the revoked set does not silently re-accept a revoked access token~~ — **cut along with the revocation-epoch mechanism itself (Section 4a)**. The scenario this test proved is now an accepted, documented risk rather than a guarded one.

Every test asserts actual output — the real HTTP response (status, `Set-Cookie` headers, body) or the real database/Redis state — not just an in-memory return value, consistent with every prior slice's testing standard.

## 6. Logs and metrics for each failure path — never the token or hash

Every failure path above gets a log line and a Micrometer counter, tagged by failure reason (`expired`, `tampered-signature`, `alg-confusion`, `reuse-detected`, `revoked`, `redis-unavailable`) — extending the same observability discipline slice 2b's review added for rejected headers. **Never logged, at any level: the raw JWT, the raw refresh token (either half — identifier or secret), the `token_hash` bytes, or the signing key.** What's safe and useful to log instead: `cmId`, `familyId` (both already meant to be visible to the CM themselves and to an operator investigating a specific session, unlike a bearer credential), and the failure reason. This mirrors the existing `extractedWallet`-never-logged discipline (CLAUDE.md) and slice 2b's "log the reason, never the raw rejected value" pattern exactly — a rejected/tampered/reused token is treated the same way a forged `Rndr-Id` header was: the fact and the reason are observable, the credential itself never is.
