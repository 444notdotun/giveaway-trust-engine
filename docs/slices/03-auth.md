## 0. Login: OAuth 2.0 Authorization Code + PKCE against X

Verified directly against X's own developer docs (fetched the actual pages):
- Authorization endpoint: `https://x.com/i/oauth2/authorize`
- Token endpoint: `https://api.x.com/2/oauth2/token`
- PKCE (`code_challenge`/`code_challenge_method`) is required, not optional, for this flow.
- Scopes requested: `users.read users.email` — `users.email` is a real, documented scope ("Email from an authenticated user"), so the CM's email is obtainable through this flow. No `offline.access` requested — this app only needs one-time identity at login, not ongoing access to the CM's X account.

Flow: redirect CM to X's authorize URL with `code_challenge`/`state` → X redirects back to our callback with `code` → server exchanges `code` (+ `code_verifier`) for an X access token via the token endpoint → server calls X's user-lookup endpoint with scopes `users.read users.email` to get `{id, username, email}` → upsert `community_manager` → issue our own access + refresh token pair (Section 2) → set cookies → redirect the CM into the app.

**Hand-rolled, not Spring Security OAuth2 Client.** This is two outbound HTTPS calls (token exchange, user lookup) using `java.net.http.HttpClient` with explicit connect/request timeouts — consistent with how this project already makes outbound HTTP calls (no Apify/Bachs SDK dependency added either; CLAUDE.md's "every external call has an explicit timeout" applies here identically). Pulling in `spring-security-oauth2-client` would mean adopting all of Spring Security for a two-call flow; not proposed.

**Schema finding, needs your sign-off before GREEN:** `community_manager` currently has no immutable X identifier — only `x_handle` (mutable; X allows handle changes) with a `UNIQUE` constraint, and `email` (`NOT NULL`, `UNIQUE`). X's user-lookup response carries both an immutable numeric `id` and the mutable `username`. Upserting by `x_handle` means a CM who renames their X handle gets a **second, disconnected `community_manager` row** on their next login, orphaning their existing giveaways/quota under the old handle. **Proposed fix: a new migration (`V2`) adding `x_user_id text NOT NULL UNIQUE` to `community_manager`, upsert keyed on `x_user_id`, with `x_handle` refreshed (not re-keyed) on every login to stay current.** This assumes no real CM rows exist on staging yet (pre-launch) — flagging that assumption rather than guessing it; if staging already has real `community_manager` rows, this migration needs a backfill strategy instead of a bare `NOT NULL`, decided before this migration ships, not during it.

**What if X doesn't return an email** (declined scope, unverified email on the X account, or any other reason the `email` claim is absent)? `community_manager.email` is `NOT NULL`. Decision: **reject the login with a clear, specific error asking the CM to verify their email with X and retry** — no placeholder email is synthesized, since a fabricated value would violate the column's own `UNIQUE` constraint the moment two emailless logins happened, and would be actively misleading data to anyone who later reads it.

## 1. Real Redis on staging

**Decision, from your answer: Render Key Value, internal URL.** Verified directly against Render's own docs (fetched, not search-summarized):
- Internal connections are **unauthenticated by default** — "the default internal connection URL doesn't include a username or password" — unless "Enable Internal Authentication" is turned on for the instance (a toggle on the instance's Info page in Render's dashboard).
- TLS (`rediss://`) is documented specifically for **external** connections ("External connections are TLS secured"); Render's docs don't describe internal connections as requiring or even offering TLS.
- Render doesn't prescribe environment variable names for consuming services — those are ours to choose, same as the existing `REDIS_HOST`/`REDIS_PORT`/`BACHS_*` pattern from slice 2a.

**Render variables to add, by name only** (staging service's env vars, set manually in Render's dashboard — this app isn't on a Blueprint/`render.yaml`, so there's no `fromService` wiring to do):
- `REDIS_HOST` — already declared in `application.properties`, currently an unconfirmed placeholder per slice 2a's open item; needs the real internal hostname of the Key Value instance once it exists (Render assigns this, e.g. shaped like `red-xxxxxxxxxxxxxxxxxxxx`).
- `REDIS_PORT` — already declared; Render's Key Value default port is `6379`.
- `REDIS_PASSWORD` — **new**, optional. Leave unset for Render's default (unauthenticated internal connection). Only needs a real value if "Enable Internal Authentication" is turned on for the instance later — Spring config below treats it as optional with an empty default, so turning that toggle on later is a one-variable change, no code change.
- `REDIS_TLS_ENABLED` — **new**, optional, defaults to `false`/unset. Not needed today per Render's docs (internal connections aren't described as TLS), included now so switching to an external connection or a different provider later is a one-variable change.

**Spring config** (`application.properties`, replacing the host/port-only placeholders):
```properties
spring.data.redis.host=${REDIS_HOST}
spring.data.redis.port=${REDIS_PORT}
spring.data.redis.password=${REDIS_PASSWORD:}
spring.data.redis.ssl.enabled=${REDIS_TLS_ENABLED:false}
spring.data.redis.timeout=2000
spring.data.redis.connect-timeout=2000
```
`spring.data.redis.timeout` is the **command** timeout (already present since slice 1/2); `spring.data.redis.connect-timeout` is **new** — the two are genuinely different failure modes (can't establish a connection at all, vs. connected but a command hangs) and CLAUDE.md requires an explicit timeout for every external call, not just one blended number. Both at 2000ms, matching the existing command timeout rather than inventing a different value without a reason to.

`DataRedisAutoConfiguration` stays **excluded only in tests that don't need Redis** (unchanged from slices 2a/2b's pattern); it is **not** excluded for the real running application, since this slice is exactly what makes Redis load-bearing (the revoked-family lookup) rather than an unused placeholder.

## 2. Tokens

**Access token: JWT, HS256, 15 minutes.** Claims: `sub` (cmId), `familyId`, `iat`, `exp` (`iat` + 15 min, computed from the injected `Clock`, never `Instant.now()`). No `jti` — access tokens aren't individually revocable (only by familyId, via the Redis set that future resolve endpoints will check), so there's nothing a per-token identifier would let us do differently.

**New dependency needed, flagging for your approval rather than adding silently:** this project has no JWT library today. Proposing **Nimbus JOSE+JWT** (`com.nimbusds:nimbus-jose-jwt`) — the library Spring's own `spring-security-oauth2-resource-server` uses internally for JWT verification, so it's already a well-vetted dependency in this exact ecosystem even though we're not adding Spring Security itself. Hand-rolling HMAC-SHA256 JWT verification ourselves is exactly how `alg: none` and signature-bypass bugs happen in practice (CLAUDE.md's own CRITICAL REVIEW list implicitly exists for reasons like this) — not proposed.

**Signing key: environment variable, no default, minimum length enforced at startup.** New `JWT_SIGNING_KEY` Render variable (see Section 1's list — this one is new, not yet declared anywhere). A new `JwtSigningKeyGuardBeanFactoryPostProcessor`, same pattern as the existing `StartupGuardBeanFactoryPostProcessor` (slice 2): refuses to start if the key is missing/blank, or shorter than 32 bytes (256 bits — the minimum HMAC-SHA256 key length security guidance actually calls for, not an arbitrary round number) once UTF-8 decoded. A separate guard class, not folded into the existing one, since each guard enforces one orthogonal invariant and slice 2's guard is already named and scoped around Bachs/environment — mixing concerns there would make a future failing assertion ambiguous about which invariant actually broke.

**Refresh token: NOT a JWT — an opaque, split identifier+secret value, 7 days, single-use, stored hashed.** The existing `refresh_token` table (`token_id`, `family_id`, `cm_id`, `used`, `expires_at` — from slice 1's migration, unchanged) already has the right shape for the identifier half; it has no column for a secret or its hash yet. **New migration (`V2`, alongside the `x_user_id` addition above) adding `token_hash bytea NOT NULL`** — SHA-256 of a freshly generated high-entropy random secret (32 random bytes), never the secret itself. SHA-256, not bcrypt/Argon2: those algorithms exist to slow down brute-forcing a *low-entropy* human-chosen secret (a password); this secret is 256 bits of CSPRNG output with no feasible brute force regardless of hash speed, so a slow KDF would only cost latency with no real security benefit.

The value actually set in the refresh cookie is `base64url(tokenId) + "." + base64url(secret)`. On refresh: split on `.`, look up the row by `tokenId`, compare `SHA-256(secret)` against the stored `token_hash` (constant-time comparison — `MessageDigest.isEqual`, not `Arrays.equals` or `.equals()`, to avoid a timing side-channel on the hash comparison itself). `tokenId` alone is never sufficient to refresh; the secret must also match.

**Rotation.** A successful refresh: an atomic conditional `UPDATE refresh_token SET used = true WHERE token_id = :id AND used = false` (the same atomic-conditional-UPDATE pattern this codebase already uses for quota claiming — CLAUDE.md: "money and quota math happens in SQL, never read then write in Java" — token single-use consumption is the identical race shape, so the identical fix applies) returning the affected row count, then — only if that update affected exactly one row — insert a new `refresh_token` row in the same `familyId` with a freshly generated `tokenId`/secret/hash and a new 7-day expiry, and issue a new 15-minute access token. **This is also the mechanism the concurrent-refresh failure test (Section 4) exercises directly**, not a separate code path invented just for that test.

**All time from the injected `Clock`.** Token expiry computation (`issuedAt.plus(Duration.ofMinutes(15))`, `issuedAt.plus(Duration.ofDays(7))`) and expiry comparison (`clock.instant().isAfter(expiresAt)`) both go through the already-established `Clock` bean — no `Instant.now()` anywhere in this slice's code, per CLAUDE.md.

## 3. Cookies

`Set-Cookie` for both the access and refresh tokens: `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/` (refresh token's path could be scoped narrower to just the refresh endpoint, but PRD doesn't call for that and this app has no other cookie-reading endpoints yet to protect against — not narrowing speculatively). Access cookie `Max-Age` matches the 15-minute token lifetime; refresh cookie `Max-Age` matches 7 days. No `Domain` attribute set (defaults to the exact host that set it — broadening to a parent domain is not something this slice needs and would only widen the cookie's blast radius for no benefit).

## 4. Revocation: database first, then Redis — CRITICAL REVIEW

**Reuse detection.** A refresh request whose conditional `UPDATE ... WHERE token_id = :id AND used = false` affects **zero** rows means one of two things: the token was already consumed by a legitimate prior rotation (this *is* the reuse case — a copy of an already-rotated token is being replayed), or the token never existed / was already revoked. Either way, the response is the same: **revoke the entire family.** `UPDATE refresh_token SET used = true WHERE family_id = :familyId` (idempotent — re-running it against an already-fully-revoked family changes nothing and is harmless, which matters because a revoked family being hit again, e.g. by an attacker retrying, must not do anything worse the second time).

**Ordering: database write commits first, Redis write second — and this is deliberate, not incidental.** The database is the durable, authoritative revocation record; Redis is a 15-minute, fast-path cache that exists only so a future resolve endpoint doesn't have to hit Postgres on every call to check a condition that's almost always false. If the DB write happens first and commits, the revocation is real and permanent regardless of what happens to the Redis write next. If the Redis write then fails (Redis down, timeout), **the refresh/reuse-detection response to the caller is unaffected** — it already reflects a durably-revoked family. The gap this leaves (an already-issued, not-yet-expired access token in that family could still pass signature+expiry checks against an endpoint that *doesn't* consult Redis) is accepted and bounded: per PRD Section 15, only resolve endpoints check the revoked set at all, and resolve endpoints are specified to **fail closed with 503 whenever Redis is unreachable** — so if Redis is down, no resolve endpoint succeeds anyway, revoked-family or not. The one case this ordering is actually protecting against is the reverse: writing to Redis first and then having the DB write fail/roll back would leave a family temporarily looking revoked in the 15-minute cache while the authoritative store never recorded it — a transient, inconsistent state with no correctness benefit over doing it the other way around.

**The Redis structure: one key per `familyId`, not a single shared Set.** PRD's phrase "revoked set" is colloquial, not a literal Redis data-structure name. A single Redis Set (`SADD`) can't give each member its own independent TTL — `EXPIRE` applies to the whole key. Since each family's revocation needs its own independent 15-minute window starting from when *that* family was revoked, the actual structure is `SET revoked:{familyId} 1 EX 900`, checked with `EXISTS revoked:{familyId}` — satisfying CLAUDE.md's "every Redis key has a TTL" literally, per key, rather than one shared key whose TTL would reset or apply incorrectly across unrelated families.

**`RevocationChecker` component, built now, consumed later.** A small component with `isFamilyRevoked(familyId): boolean`, reading the key above, with an explicit connect+command timeout (Section 1) — on any Redis failure (timeout, connection refused), it throws a dedicated `RevocationCheckUnavailableException` rather than defaulting to `false` (which would silently fail open) or `true` (which would needlessly lock out every CM on a Redis blip). A `@ControllerAdvice` maps that exception to `503`, built now so every future resolve endpoint gets this behavior automatically just by calling `isFamilyRevoked(...)`, with no per-endpoint boilerplate to get right or forget.

**Honest scope boundary, carried forward:** no resolve endpoint exists yet (first one arrives in a later slice). This slice proves the `RevocationChecker` → `503` path at the component/exception-mapping level (Section 5's Redis-down failure test), the same way slice 2a left its three staging failure cases honestly marked "not yet demonstrated end-to-end" rather than fabricated against infrastructure that didn't exist. The first slice that adds a real resolve endpoint should re-prove this against that actual endpoint, not just trust this slice's component-level proof transitively.

## 5. Failure tests, written first — shown red before any implementation

1. **Two concurrent refreshes with the same token: exactly one wins, the other triggers reuse handling.** Two threads call the refresh path with the identical `tokenId`/secret at the same time; assert exactly one receives a new rotated token pair, the other receives the reuse-detected response, and afterward every token in that family has `used = true` in the database — proving the atomic conditional `UPDATE` actually serializes the race rather than both threads reading `used = false` and both proceeding.
2. **Reuse of a rotated token revokes the whole family.** Refresh once (rotates token A → token B, A now `used = true`). Present token A again; assert every token in the family (including B, not yet expired or used by anyone) is now `used = true`, and that a subsequent refresh attempt using B also fails.
3. **A revoked token is rejected.** After family revocation, any further refresh attempt against any token in that family fails — not just the originally-reused one.
4. **An expired access token is rejected** — signature valid, `exp` in the past (relative to the injected `Clock`, not wall-clock `Instant.now()`, so this test controls time deterministically rather than sleeping).
5. **A tampered signature is rejected** — flip one byte of a validly-issued token's signature segment; must fail verification, not fail at some later unrelated step.
6. **Algorithm confusion (`alg: none`) is rejected.** Hand-construct a token with header `{"alg":"none"}` and no signature segment, claiming a valid `cmId`/`familyId`; Nimbus's verifier must reject this outright because the library is configured to accept only `HS256` and never trusts the token's own `alg` header to pick a verification strategy — the exact class of bug a hand-rolled verifier would be likely to get wrong.
7. **Redis down gives 503, not 200 (or a silent fail-open).** Point `RevocationChecker` at an unreachable Redis (wrong port, or a Testcontainers Redis container stopped mid-test); assert `isFamilyRevoked(...)` throws `RevocationCheckUnavailableException`, and that the `@ControllerAdvice` mapping produces a `503` response, not a `200`/`401` that would mean "not revoked" or "revoked" respectively — either of which would be a wrong, Redis-outage-shaped guess instead of an honest failure.
8. **Cookie flags are asserted directly**, not assumed from code review: parse the real `Set-Cookie` header(s) from a real login/refresh response and assert `HttpOnly`, `Secure`, and `SameSite=Strict` are all literally present, for both the access and refresh cookies.
9. **`userId`/`cmId` always comes from the verified JWT, never from a request body or path parameter.** Craft a request whose body or path claims a different `cmId` than the one in the caller's own valid JWT; assert the JWT's `cmId` is what's actually used (there's no endpoint in this slice that varies behavior by a body/path-supplied `cmId` yet, so this is tested at the extraction-point level — the component that pulls `cmId` out of the authenticated request context never reads it from anywhere else — with a note that every future endpoint built on top of this must be reviewed to confirm it never introduces a body/path `cmId` field that silently shadows it).

Every test asserts actual output — the real HTTP response (status, `Set-Cookie` headers, body) or the real database/Redis state — not just an in-memory return value, consistent with every prior slice's testing standard.

## 6. Logs and metrics for each failure path — never the token or hash

Every failure path above gets a log line and a Micrometer counter, tagged by failure reason (`expired`, `tampered-signature`, `alg-confusion`, `reuse-detected`, `revoked`, `redis-unavailable`) — extending the same observability discipline slice 2b's review added for rejected headers. **Never logged, at any level: the raw JWT, the raw refresh token (either half — identifier or secret), the `token_hash` bytes, or the signing key.** What's safe and useful to log instead: `cmId`, `familyId` (both already meant to be visible to the CM themselves and to an operator investigating a specific session, unlike a bearer credential), and the failure reason. This mirrors the existing `extractedWallet`-never-logged discipline (CLAUDE.md) and slice 2b's "log the reason, never the raw rejected value" pattern exactly — a rejected/tampered/reused token is treated the same way a forged `Rndr-Id` header was: the fact and the reason are observable, the credential itself never is.
