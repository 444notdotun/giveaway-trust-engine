# Slice 4: Quota

CRITICAL REVIEW. PRD refs: Section 4.2 (Atomic Quota Claim), Section 4.3 (AccountQuota fields and operations — `claimRoll`, `refundRoll`, `addRolls`), Section 4.5 (Billing Abstraction — `addRolls()` is built here; the Bachs webhook that calls it is slice 10), Section 10 (Risks — "server crash between roll claim and refund"), Section 11 (Acceptance Criteria — Quota gate, Atomic quota claim, Roll refund on failure). BUILD_ORDER item 4: "claimRoll as one conditional UPDATE, refundRoll as SQL decrement. Concurrency test: many threads, one roll left, exactly one success, rolls_used never exceeds rolls_allocated." BUILD_ORDER's slice 10 line ("addRolls on success") describes slice 10 *calling* `addRolls`, the same relationship slice 5 has to `claimRoll` — the primitive is defined and reviewed here; the caller arrives later.

No migration in this slice. `account_quota` and its three CHECK constraints (`rolls_allocated >= 0`, `rolls_used >= 0`, `rolls_used <= rolls_allocated`) already exist from slice 1 (`V1__initial_schema.sql`). This slice is service-layer only: three methods — `claimRoll`, `refundRoll`, `addRolls` — on an existing table.

## 1. Bad path first

**Worst production failure: a roll is claimed, the process crashes before the giveaway either finalizes a status or gets refunded, and the CM is now permanently charged for nothing.** This is PRD's own named risk (Section 10: "Server crash between roll claim and refund leaves the CM charged — known gap in v1, detected via `giveaway_logs`, refunded manually, sweeper proposed"), not a risk this slice invents.

The failure window this slice is responsible for bounding is narrow and specific: `claimRoll` itself is a single SQL statement, so it cannot itself be interrupted mid-way — it either commits (one row updated) or it doesn't (zero rows, nothing changed). The actual crash window PRD is worried about opens **after** `claimRoll` returns `true` and **before** whatever called it (the Create Giveaway endpoint, slice 5) either calls `refundRoll` (on ingestion failure) or finalizes the giveaway. That orchestration doesn't exist yet — it's slice 5's job. What slice 4 owns and must get right now is making sure the primitives that window depends on are themselves atomic, SQL-level, and impossible to leave half-applied: `claimRoll` never partially claims, `refundRoll` never partially refunds, and neither can ever push `rolls_used` outside `[0, rolls_allocated]`, no matter how many callers hit them at once or how a caller's own crash timing lines up.

**A second, related risk this slice can only partly close: double refund.** `refundRoll`'s guard (Section 5) stops a refund from ever driving `rolls_used` negative, but it cannot tell a legitimate refund apart from an accidental second refund of the same already-refunded claim — both look identical to the database. Closing that gap is explicitly slice 5's job, not this one's (Section 5 states the exact requirement).

**No sweeper is built in this slice, or proposed to be built in any slice in BUILD_ORDER.** The crash-between-claim-and-refund gap PRD names stays open after slice 4 — this slice makes the primitives trustworthy; it does not close the orchestration-level gap PRD already accepts as a known v1 risk.

`addRolls` carries comparatively little of this slice's risk: the Bachs webhook that will call it (slice 10) is protected upstream by `payment_event`'s `(provider, event_id)` unique constraint, so a redelivered webhook never reaches `addRolls` twice for the same event. What this slice still owes `addRolls` is the same thing it owes the other two: a genuinely atomic SQL increment, not a read-then-write that could lose an update under concurrent credits.

## 2. Failure modes

| Failure | Detection | Graceful degradation |
| --- | --- | --- |
| No roll left (`rolls_used == rolls_allocated`) | `claimRoll`'s conditional `UPDATE` affects zero rows | Returns `false`/zero-rows to the caller, who maps it to HTTP 402 (slice 5) — not this slice's endpoint, but the primitive's own return contract. Nothing is written; no retry needed. |
| Two simultaneous claims race for the last roll | Postgres's own row-level locking inside the single `UPDATE ... WHERE rolls_used < rolls_allocated` serializes the two statements — the loser's `WHERE` clause simply no longer matches once the winner commits | Loser gets zero-rows-affected, identical to "no roll left" — no distinguishable error, no partial state, no deadlock (both touch the same single row, same statement, no multi-statement transaction to deadlock across). |
| Refund attempted when `rolls_used` is already 0, including a double refund of the same claim | `refundRoll`'s conditional `UPDATE ... WHERE rolls_used > 0` affects zero rows | Returns zero-rows, no exception — but this is **not** proof a double refund was caught; it only proves the value never went negative. The guard cannot distinguish "nothing to refund" from "already refunded this one." See Section 5's hard contract. |
| `addRolls` called with a non-positive amount | Application-level precondition check, before any SQL is issued | Rejected immediately with a clear, typed exception. No row touched, no DB round trip spent on an invalid request. |
| DB connection/statement failure during `claimRoll`, `refundRoll`, or `addRolls` | `SQLException` caught at the call site | Logged with `reason=db-unavailable` and a `giveaway.quota.failure` counter increment (same pattern as slice 3's `recordFailure`), rethrown as the same internal unchecked exception slice 3 already established (`IllegalStateException`) so the caller fails closed rather than guessing the claim succeeded. |
| A statement blocked on a row lock (e.g. a concurrent `refundRoll` or an unrelated long-running transaction touching the same `account_quota` row) | The same `connection-init-sql`-configured `statement_timeout` every other DB call in this project already carries (slice 3, item 5) bounds this one too — no new mechanism needed | Fails within the existing bound (5s in production, per `application.properties`), surfaces as the same `db-unavailable` path above, not an indefinite hang. **Unverified against the real Supabase session pooler** — same open caveat slice 3 already carries forward; this slice adds no new verification of it, only another caller of the same unverified mechanism. |
| `cmId` with no matching `account_quota` row at all | `claimRoll`/`refundRoll`'s `UPDATE` affects zero rows, indistinguishable from the guard legitimately tripping — disambiguated by one `SELECT 1` on `account_quota` for that `cmId`, run only on the zero-rows path (Section 4, test 8). `addRolls` has no guard to confuse this with, so its own zero-rows result is already unambiguous. | Structurally should never happen — `CommunityManagerRepository.upsertByXUserId` creates the `account_quota` row in the same transaction as a new `community_manager` row (slice 3), and the `uq_account_quota_cm_id` constraint makes it 1:1. Tested anyway as a defensive case so a future regression that breaks this invariant fails loudly in a test, not silently in production. |

## 3. Who uses it, what breaks under load

**Today: only this slice's own test harness.** Slice 4 adds no HTTP endpoint — `claimRoll`, `refundRoll`, and `addRolls` are plain Java methods tested directly against a real Postgres (Testcontainers), per BUILD_ORDER's own framing ("concurrency test: many threads"), not through a controller.

**The real callers, once they exist:** the Create Giveaway endpoint (slice 5) calls `claimRoll` once per request, before the synchronous Apify call, and `refundRoll` if ingestion then fails — under the exactly-once-per-failed-giveaway contract Section 5 states. The Bachs webhook (slice 10) calls `addRolls` on a successful payment event.

**What breaks under load:** nothing new, if `claimRoll`'s and `addRolls`' atomicity hold — that's the entire point of their concurrency tests. If `claimRoll` doesn't hold (e.g. a future regression reintroduces a read-then-write), many simultaneous Create Giveaway requests against one remaining roll would let more than one succeed, each triggering a real Apify call this project pays for, and `rolls_used` could exceed `rolls_allocated` — a direct money leak, not just a logic bug. If `addRolls` doesn't hold, two near-simultaneous successful payments for the same CM could lose one credit entirely. This is exactly why BUILD_ORDER marks this slice CRITICAL REVIEW and names the concurrency test explicitly rather than leaving it implied.

## 4. Tests — RED first, stub-based, mutation check per critical rule

All run against a real Postgres via Testcontainers (no mocked `DataSource`) — this slice's entire correctness claim is about real database locking behavior, which nothing else can substitute for.

1. **`claimRoll` succeeds and increments `rolls_used` by exactly one**, when `rolls_used < rolls_allocated`. RED first: no `AccountQuotaService`/equivalent class exists yet.
2. **`claimRoll` returns false/zero-rows when no roll is left** (`rolls_used == rolls_allocated`) — no row is modified, no exception thrown. **Mutation check:** remove the `WHERE rolls_used < rolls_allocated` condition and confirm this test now fails with a `SQLException` from `ck_account_quota_rolls_used_le_allocated` firing instead of a clean zero-rows result — proving the guard, not the constraint, produces the clean rejection in normal operation.
3. **Concurrency test (the one BUILD_ORDER names directly).** Pool size at least the thread count (so pool exhaustion can never be what's actually serializing the threads, masking a real race the same way slice 3's statement-timeout proof was once accidentally masked) — 50 threads, one roll left, each blocked on a shared `CountDownLatch` until every thread has started, then released together so the race is genuinely simultaneous, not trickled. Assert exactly 1 returns true, the other 49 return false cleanly, and `rolls_used` afterward equals exactly `rolls_allocated`. **Mutation check for the critical rule ("claimRoll is one conditional UPDATE, not check-then-update"):** temporarily rewrite `claimRoll` to `SELECT` the current value, increment in Java, then `UPDATE` — rerun this exact test, confirm it now fails (more than one thread succeeds, or `rolls_used` exceeds `rolls_allocated`), confirming the test actually exercises the "money math happens in SQL" rule (CLAUDE.md) rather than passing by coincidence. Revert and reconfirm green.
4. **Claim-and-refund interleave.** With several rolls available, concurrently call `claimRoll` and `refundRoll` against the same `cmId` from different threads (e.g. claim, claim, refund, claim racing against each other) and assert `rolls_used` only ever reflects legitimate completed operations — never a lost update, never a value outside `[0, rolls_allocated]`, no deadlock between the two different statements touching the same row. Run in a loop 20 times (this is exactly the kind of interleaving timing bug that can pass once and flake later; a single green run proves little on its own).
5. **`refundRoll` succeeds and decrements `rolls_used` by exactly one** via its conditional `UPDATE ... SET rolls_used = rolls_used - 1 WHERE cm_id = ? AND rolls_used > 0`.
6. **`refundRoll` over-refund returns zero rows, no exception.** With `rolls_used` already at 0, `refundRoll` returns zero-rows cleanly — the guard's job, stated plainly: **it stops a negative value, it does not detect or prevent a double refund.** **Mutation check:** remove the `AND rolls_used > 0` condition and confirm the test above now fails — not with a clean zero-rows result, but with a `SQLException` from `ck_account_quota_rolls_used_nonneg` firing instead, proving the guard (not the database constraint) is what produces the clean rejection path in normal operation, while the constraint is the backstop if the guard is ever removed. **Added after the first review round (reviewer finding 1):** this path also logs a WARN naming `reason=refund-noop` and increments `giveaway.quota.failure{reason=refund-noop}` — it was silent before, and it is the one path a double refund would ever leave a trace on.
7. **A blocked `claimRoll`/`refundRoll` fails within the existing `statement_timeout` bound, not indefinitely.** A second connection holds the row lock on the target `account_quota` row (open, uncommitted transaction); `claimRoll` against the same row must fail within the configured bound. **Mutation check:** reuses slice 3's established pattern (`HikariConnectionInitSqlStatementTimeoutTest`) rather than re-litigating it — this test only confirms the *existing* mechanism actually covers `account_quota` statements too, not re-prove the mechanism itself. **Unverified against the real Supabase session pooler** — same caveat slice 3 already carries; not re-verified here.
8. **Missing `account_quota` row disambiguation.** On the zero-rows path only (`claimRoll` or `refundRoll` affected zero rows), run one `SELECT 1 FROM account_quota WHERE cm_id = ?`. If that also finds nothing, throw a clear, typed exception (a genuine data-integrity bug, not a quota rejection) rather than silently behaving as if the roll-exhausted/already-refunded guard had simply tripped. The happy path (a successful claim or refund) never runs this extra query — it stays exactly one statement, same as before. **Added after the first review round (reviewer finding 2):** this path, in all three methods (`claimRoll`, `refundRoll`, `addRolls`), now logs a WARN naming `reason=missing-quota-row` and increments `giveaway.quota.failure{reason=missing-quota-row}` *before* throwing — it threw silently before, with no trace at all, despite being the single most serious failure class this slice defines.
9. **Observability: failure paths.** The DB-failure path logs a WARN naming `reason=db-unavailable` and increments `giveaway.quota.failure{reason=db-unavailable}`. The "no roll left" rejection is **not** a WARN — see test 10 — but still increments `giveaway.quota.failure{reason=exhausted}`. Asserted the same way slice 3's `RefreshEndpointTest`/`OAuthLoginFlowTest` assert theirs: `CapturedOutput` for the log line, a `MeterRegistry` before/after delta for the counter. RED first — no counter exists yet.
10. **The "exhausted" outcome logs at INFO, not WARN.** A brand-new CM at `0/0` hitting the quota gate is a normal business outcome, not an operational problem — logging it as a WARN would mean every single new signup's first create-giveaway attempt logs a warning for no reason. The log line still names `reason=exhausted`, and the counter `giveaway.quota.failure{reason=exhausted}` still increments exactly as before — only the log *level* changes. Asserted by capturing output at INFO and confirming no WARN-level line exists for this path.
11. **Observability: success paths.** `claimRoll` and `refundRoll` each log one structured INFO line on completion — `cmId` and the outcome only (`claimed`/`refunded`), nothing else — so the QA team's clarification on quota concurrency can actually be acted on: a server crash between claim and refund has no automatic recovery, detection relies on log lines, and any lost roll is refunded manually.
12. **No secret or personal data in any of the above log lines.** `cmId` is safe to log (same reasoning slice 3 already applied to `familyId` — a correlation id meant to be visible to an operator, never a bearer credential). Nothing else exists on `AccountQuota` to leak at this stage (no wallet, no payment detail, no token) — this test exists mainly to lock that in before slice 10 adds `amountCents`/`providerReference`, which must **not** be logged by anything built here or later without its own explicit review.
13. **`addRolls` succeeds and increments `rolls_allocated` by exactly the given amount** via `UPDATE account_quota SET rolls_allocated = rolls_allocated + ? WHERE cm_id = ?`.
14. **`addRolls` rejects an amount of zero or less** before issuing any SQL — a clear, typed exception, no row touched, no DB round trip spent.
15. **`addRolls` on a missing `cmId` throws a clear exception directly** on zero-rows-affected — unlike `claimRoll`/`refundRoll`, there is no guard condition to disambiguate from (the only `WHERE` clause is the `cmId` match itself), so no extra `SELECT 1` is needed here; zero rows can only mean one thing.
16. **`addRolls` concurrency test.** Many threads call `addRolls` with different amounts against the same `cmId` simultaneously; assert the final `rolls_allocated` equals the starting value plus the exact sum of every amount — no lost update. **Mutation check:** rewrite as `SELECT`-then-`UPDATE`, confirm this test now fails (the final total is short), confirming the increment is genuinely SQL-level, not a Java-side read-modify-write.

## 5. Timeouts, idempotency, observability

**Timeouts.** No external call exists in this slice — `claimRoll`, `refundRoll`, and `addRolls` are each one SQL statement (plus, on the rare zero-rows path, one extra `SELECT 1` for `claimRoll`/`refundRoll`) against the local Postgres. The only timeout that applies is the connection-level `statement_timeout` every DB call in this project already carries (slice 3, item 5's `connection-init-sql` mechanism) — test 7 above confirms it actually covers these statements too; nothing new is configured. As stated there and in slice 3's own doc, this mechanism is **unverified against the real Supabase session pooler** — this slice does not change or re-verify that.

**Idempotency — the hard contract.** `refundRoll`'s `WHERE rolls_used > 0` guard prevents exactly one thing: a negative `rolls_used` value. It does **not** detect, prevent, or even notice a double refund — a second `refundRoll` call for a claim already refunded once looks, to the database, identical to any other legitimate refund, as long as `rolls_used` stays above zero. **This slice does not solve double-refund safety. It is an explicit requirement on slice 5:** the caller must call `refundRoll` exactly once per failed giveaway, and that call must happen in the same transaction as the giveaway's own state change to `FAILED` — so a crash between the two can never leave one without the other, and so a retry of the failure-handling path itself can never issue a second, phantom refund. `claimRoll` carries the mirror version of the same discipline: it is deliberately not idempotent (each call claims one additional roll), and calling it twice for one logical "create giveaway" attempt is a caller bug slice 5 must not allow, not something this slice's primitives can guard against from underneath. `addRolls` is lower-risk by construction — `payment_event`'s own `(provider, event_id)` unique constraint (slice 1) already stops a redelivered webhook from ever reaching `addRolls` twice for the same event — but `addRolls` itself still owes atomicity under concurrent, legitimately-different credits (test 16).

This remains a real, named gap at the orchestration level (PRD Section 10's "known gap in v1," the proposed-but-unbuilt sweeper) even once slice 5 honors the contract above — a crash can still happen between the refund call and the giveaway-state write if slice 5 doesn't genuinely wrap both in one transaction. That risk is slice 5's to close, not this slice's to pretend is already closed.

**Slice 5 hard requirements, stated here because this slice's own primitives cannot enforce them:**

(a) **Refund only if the giveaway's own state transition actually happened.** Slice 5 must call `refundRoll(cmId)` only after `UPDATE giveaway SET status = 'FAILED' WHERE id = ? AND status = 'PROCESSING'` has changed **exactly one row**, and both statements must run in the **same transaction**. A conditional state transition that changes zero rows (the giveaway was already `FAILED`, already resolved by another request, or never reached `PROCESSING`) must never be followed by a refund call — that is precisely the shape of a double refund this slice's guard cannot catch on its own. Wrapping both in one transaction is also what makes the crash-between-the-two-calls risk (above) actually bounded: either both commit or neither does.

(b) **Never return an exception message in an HTTP response.** Every exception this slice throws (`IllegalStateException` for a DB failure or a missing `account_quota` row, `IllegalArgumentException` for an invalid `addRolls` amount) carries an internal message that may name a `cmId` or an internal invariant. Slice 5's exception handling must map these to a generic status code and body (402/503/500 as appropriate) and must never call `exception.getMessage()` (or let a default Spring error handler do so) into anything a client receives.

**Observability.** `giveaway.quota.failure{reason=...}` — one counter name reused by every failure path (`exhausted`, `db-unavailable`, `refund-noop`, `missing-quota-row`), matching slice 3's final-fixes-round lesson (one counter name per failure family, not a separate one per class) rather than repeating the `giveaway.oauth.failure`/`giveaway.auth.failure` split that round had to go back and fix. **Log level differs by reason, the counter does not:** `db-unavailable` and `missing-quota-row` log at WARN (both are operational problems — the second one specifically a data-integrity bug that should structurally never happen); `refund-noop` also logs at WARN, since an over-refund attempt (including a double refund) is exactly the signal an operator needs to see, even though the guard cannot tell a double refund apart from any other no-op; `exhausted` logs at INFO (a new CM at `0/0`, or any CM who has simply spent their rolls, hitting the quota gate is a normal business outcome, not an operator-facing warning). Every log line names `cmId` and nothing else — never the raw SQL, `rolls_used`/`rolls_allocated` values, or any future payment/wallet field. Every successful claim or refund also logs one INFO line with `cmId` and the outcome, giving the QA team's described manual-refund workflow — detection relies on log lines, since a crash between claim and refund has no automatic recovery — something to search.

## 6. Explicitly out of scope

- **The Create Giveaway HTTP endpoint**, its `402` response, and the claim-then-call-Apify orchestration. Slice 5.
- **The exactly-once refund-in-the-same-transaction-as-the-state-change discipline itself.** This slice states the requirement (Section 5) and builds the guard that makes a violation of it merely silent rather than also corrupting the row; enforcing it is slice 5's implementation, not this slice's. Concretely, slice 5 must: (a) call `refundRoll` only after confirming `UPDATE giveaway SET status = 'FAILED' WHERE id = ? AND status = 'PROCESSING'` changed exactly one row, both statements in the same transaction; (b) never let any exception message from this slice (`IllegalStateException`, `IllegalArgumentException`) reach an HTTP response body.
- **The Bachs webhook, `PaymentGateway`, `createCheckoutSession`, and anything from PRD Section 4.5 beyond `AccountQuota` itself.** Slice 10 — `addRolls` is built here, but nothing calls it until then.
- **The crash-recovery sweeper** PRD Section 10 proposes for claimed-but-never-refunded rolls. Not built here; not built in any slice BUILD_ORDER currently names. Stays an accepted, open gap after this slice.
- **Any new migration.** `account_quota` and its three CHECK constraints already exist (slice 1). This slice adds no schema change.
- **Verifying `statement_timeout` against the real Supabase session pooler.** Still unverified, same as slice 3; this slice adds another caller of the mechanism, not a verification of it.
- **Pricing tiers, margin figures, or anything from PRD Section 8.** Not quota's concern at the primitive level — the actual `amount` values `addRolls` is called with are decided by the checkout flow (slice 10), not by this slice.
